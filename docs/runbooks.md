# Runbooks

Every alert that can reach a human links here (`pint` enforces it for pages). Each entry answers
three questions: **what is broken, how do I confirm it, what do I do.**

Quick links: Grafana http://127.0.0.1:3030 · Prometheus http://127.0.0.1:9091 ·
Alertmanager http://127.0.0.1:9094 · Mailpit http://127.0.0.1:8025 ·
collector zPages http://127.0.0.1:55679/debug/pipelinez

---

## provider-budget-burn

**Alerts:** `InaturalistAvailabilityBudgetBurn`, `…LatencyBudgetBurn`, `…FreshnessBudgetBurn` and the
same for `Wikimedia*`, `Mastodon*`, `Gbif*` (generated by Sloth from `slos/*.yml`).

**What it means.** A public API we depend on is spending its error budget faster than the SLO
allows. `sloth_severity=page` = fast burn (14.4× over 1 h or 6× over 6 h), `sloth_severity=ticket`
= slow burn (3× over 1 d or 1× over 3 d). These are someone else's systems, so the fast tier opens a
ticket and the slow tier is recorded only (see [slo-decisions.md](slo-decisions.md#who-gets-woken-up)).

**Confirm.**
1. SLO dashboard → filter the service → burn rate panel: which windows are above the dashed lines?
2. *Probe result* state timeline: hard failures (red) or slow successes (latency SLO)?
3. *Where the time goes*: if DNS/TCP/TLS grew, it is the network path; if "server + transfer"
   grew, it is the provider.
4. Try it yourself: `curl -sw '%{http_code} %{time_total}s\n' -o /dev/null '<url from the alert>'`.

**Act.**
- Provider outage → nothing to fix. Check the provider's status page/forum, add a note to the
  ticket, and let `ProviderUnreachable` inhibit the noise.
- Our side (DNS, network, proxy) → fix it; the budget recovers by itself.
- Persistent slow burn with no user impact → the objective or threshold is wrong. Follow the
  [error budget policy](error-budget-policy.md#revisiting-an-slo) instead of silencing it.

## contract-broken

**Alerts:** `ProviderContractBroken`, `*CorrectnessBudgetBurn`.

**What it means.** The API answers `200 OK`, but the payload no longer matches the gjson
validations in `otel-collector/config.yaml` (e.g. the newest observation in a fungi query is not a
fungus, a field disappeared, the structure changed).

**Confirm.** Fetch the probe URL and compare with the validations:
```bash
curl -s 'https://api.inaturalist.org/v1/observations?taxon_id=47170&place_id=7800&per_page=1&order_by=id&order=desc' | jq '.results[0].taxon.iconic_taxon_name, .results[0].place_ids'
```
`docker compose logs json-exporter` shows JSONPath errors if the consumer side broke too.

**Act.** If the provider changed its schema on purpose, update the JSONPath in
`json-exporter/config.yml`, the validations in the collector config, and the unit tests. If the
data is temporarily wrong upstream, wait — correctness has its own budget.

## dashboard-latency

**Alert:** `DashboardLatencyBudgetBurn` (page).

**What it means.** More than 1 % of Grafana's `POST /api/ds/query` requests (the data behind every
panel) take longer than 2 s.

**Confirm.** Platform dashboard → *latency percentiles*: click an exemplar dot above the 2 s line →
the trace opens in Tempo. The waterfall shows which datasource was slow:
- `prometheus` spans → an expensive query (look for long ranges over raw series),
- `yesoreyeram-infinity-datasource` → a public API behind an Infinity panel is slow.

**Act.** Expensive PromQL → add a recording rule. Infinity → raise the panel's cache/refresh
interval or move the data into Prometheus via json-exporter.

## dashboard-freshness

**Alert:** `DashboardFreshnessBudgetBurn` (page).

**What it means.** The newest iNaturalist sample in Prometheus is older than 10 minutes too often.
Anything in the chain can cause it: API → json-exporter → collector → OTLP → TSDB.

**Confirm (walk the chain).**
1. `ProviderUnreachable{provider="inaturalist"}` firing? Then it's upstream (this alert is
   inhibited in that case).
2. http://127.0.0.1:55679/debug/pipelinez → is `metrics/forest` receiving?
3. `docker compose logs --tail=50 otel-collector json-exporter`.
4. Prometheus → `up{job="inaturalist"}` and `prometheus_http_requests_total{handler="/api/v1/otlp/v1/metrics"}`.

**Act.** Restart the broken component (`docker compose restart <service>`); if OTLP writes are
rejected, see [telemetry-ingestion](#telemetry-ingestion).

## alert-delivery

**Alerts:** `AlertDeliveryBudgetBurn`, `AlertPipelineHeartbeatMissing` (page).

**What it means.** Notifications are not leaving Alertmanager, or are not arriving in the
mailbox. Real alerts may be firing that nobody sees — **check the Alertmanager UI directly**
(http://127.0.0.1:9094), not your inbox.

**Confirm.**
- `docker compose logs --tail=50 alertmanager | grep -i notify` — SMTP errors?
- Mailpit up? http://127.0.0.1:8025 — heartbeat e-mails every 5 min?
- Platform dashboard → *Alert e-mails* panel: sent vs failed vs received.

**Act.** Restart Mailpit/Alertmanager. In production the Watchdog would also go to an external
dead man's switch (healthchecks.io, Cronitor, PagerDuty) — this alert can't reliably mail itself.

## telemetry-ingestion

**Alerts:** `TelemetryIngestionBudgetBurn` (page), `CollectorExportQueueFilling`,
`CollectorRefusingData`, `PrometheusOTLPIngestionErrors`.

**What it means.** Metric points are lost between the collector and Prometheus.

**Confirm.**
- `docker compose logs otel-collector | grep -i -E "error|dropping|refused"`.
- Prometheus logs: `out of order sample`, `too old sample`, `invalid metric name`.
- Collector memory panel: RSS near the `memory_limiter` limit → receivers refuse data on purpose.

**Act.** Out-of-order → check clocks / raise `storage.tsdb.out_of_order_time_window`. Memory →
lower scrape volume or give the container more memory. Prometheus down → see
[component-down](#component-down).

## telemetry-pipeline-down

**Alert:** `TelemetryPipelineDown` (page).

**What it means.** The OpenTelemetry Collector is gone. No forest data, no probes, no traces, no
logs. Prometheus still sees it because it scrapes the collector directly.

**Act.** `docker compose ps otel-collector`, `docker compose logs --tail=100 otel-collector`.
A config error after an edit is the usual cause: `docker compose run --rm otelcol-validate`, fix,
`docker compose up -d otel-collector`.

## component-down

**Alert:** `PlatformComponentDown`.

**Act.** `docker compose ps`, `docker compose logs --tail=100 <job>`,
`docker compose up -d <job>`. Validate configs before restarting:
`make check` (or the individual `docker compose run --rm …` tools).

## provider-unreachable

**Alert:** `ProviderUnreachable`.

**What it means.** Every synthetic probe of one provider failed for 15 minutes. Root cause alert:
Alertmanager inhibits that provider's SLO burn and data-quality tickets while it fires.

**Act.** Confirm from your machine with `curl`. If it's down for everyone, wait and note the
outage in the ticket. If only for you, check DNS/proxy/firewall.

## count-dropped

**Alert:** `ObservationCountDropped`.

**What it means.** An iNaturalist total fell by more than 1 % within an hour. Totals usually only
grow; a drop means a re-index, a bulk deletion or a changed query. `delta()`-based panels will show
a dip; `increase()` would have shown a huge spike (see `tests/forest_test.yml`).

**Act.** Usually nothing — note it. If the query changed (taxonomy update merged two taxa), update
the `taxon_id` in `otel-collector/species.yml`.

## consumer-scrapes-failing

**Alert:** `ConsumerScrapesFailing`.

**What it means.** json-exporter fails more than 20 % of its fetches for a provider while the
synthetic probe succeeds. Typical causes: the provider throttles our User-Agent, a bigger response
times out (30 s scrape timeout), or a JSONPath no longer matches.

**Act.** `docker compose logs json-exporter | grep -i error`. Test one module by hand:
`curl 'http://<json-exporter>:7979/probe?module=wiki_pageviews&target=<url>'` from a container on
the compose network.

## rate-limited

**Alert:** `UpstreamRateLimited`.

**Act.** Increase `scrape_interval` for that job in `otel-collector/config.yaml` (and
`collection_interval` of `http_check`), then `docker compose restart otel-collector`. The polling
budget per provider is in the README.
